# Agent assignment interface decisions

[Proposal](2.1-agent-schedule-commands.md) · [Original Owner requirements](2.1-agent-schedule-commands.md#8-original-owner-requirements) · [Delivery references](2.1-agent-schedule-commands.status.md)

The [decision-record standard](../../standards/documentation.md#decision-records) governs these footers. Unknown attribution and dates remain null; combined approval dates stay in their source evidence. Recording time identifies this revision.

## 1. Identity and storage

Identify an assignment independently of its directory and qualify every Schedule by repository. This prevents collisions when issue numbers repeat across repositories and allows an assignment to survive loss of a view.

The original proposal selects immutable assignment IDs, versioned records, atomic writes and per-assignment locking in a per-user data store. The standalone launcher instead stores a native background ID in a per-schedule state file.

**Alternatives and consequences:** retain the standalone binding, adopt the structured assignment store, or define a compatibility layer. The storage decision must identify the authoritative record and preserve native session identity. A documentation rewrite does not select a migration.

## 2. Terminal lifetime

The original assignment proposal reuses an assignment-marked tmux environment and retains its companion shell. The standalone launcher creates a fresh view on every attached start and uses `destroy-unattached`.

**Alternatives and consequences:** reuse favors shell continuity; fresh views provide a separate shell for each start. The choice must define detach, missing-view recovery, simultaneous clients and ownership checks. Either design must retain one assigned native conversation without replaying initialization.

## 3. Commands and binding changes

The sketches use both AgentSchedule and AgentAssignment. Final names are not selected.

A decision must also specify whether removal ends existing views, how reassignment treats a running native session, whether an occupied Schedule binding is refused or replaced, and which command creates the first agent session. Replacing a binding can orphan or duplicate work; it must not be inferred from a command name.

The supported GitHub Schedule-creation command is independent of those naming choices.

## 4. Read-only retrieval and adapters

Separate local runtime observations from GitHub progress and expose the same information through shell JSON and PowerShell objects. Per-assignment failures remain visible without discarding other results.

Keep agent-specific availability, startup, ID discovery, resumption and process checks behind adapters. The shared command layer owns assignment identity and retrieval.

**Alternatives and consequences:** agent-specific command suites would duplicate storage and state handling. The shared interface reduces that duplication but requires each adapter to state its supported observations. Unknown runtime state cannot be replaced with terminal-text guesses.
