# 2.1 The agent-schedule commands — a claude session's binding to its schedule, as CRUD

> **Status:** sketched, 2026-10-13 and 2026-10-14; not started. Companion:
> [`2.1-agent-schedule-commands.status.md`](2.1-agent-schedule-commands.status.md). Work:
> [NobleFactor/noblefactor-ops#302](https://github.com/NobleFactor/noblefactor-ops/issues/302). Feature:
> [NobleFactor/noblefactor-ops#151](https://github.com/NobleFactor/noblefactor-ops/issues/151).
>
> **Relationship to the neighbors.** [2. Command line](2-command-line.md) is the command these follow, and its store
> theirs; [1. Session model](1-session-model.md) is the lifecycle they manage.

Start-Claude is the first of a set of commands the owner has sketched, preliminary, on 2026-10-13 and 2026-10-14:
four that create, read, update and delete a claude session's binding to its schedule, the store's entry, and one
that acts on it. The owner, 2026-10-14: "If there is no schedule on a session, you must set one."

| Command | What it does | Today's form |
| --- | --- | --- |
| `Get-AgentSchedule` | Lists the claude sessions on a machine, the schedule of each, their tmux sessions, and the work underway | No command; the store is read by hand |
| `New-AgentSchedule` | Opens a new schedule | `Start-Claude --schedule new` |
| `Remove-AgentSchedule` | Breaks a session's binding to its schedule; the GitHub schedule and the claude session remain | No command |
| `Set-AgentSchedule` | Puts an existing claude session on a schedule, or changes its schedule, and writes the store's entry | `Start-Claude --resume <id> --schedule <key>`, which only adds one |
| `Start-AgentSchedule` | Starts the schedule's session, or attaches to it | `Start-Claude --schedule <key>` |

Open on NobleFactor/noblefactor-ops#302: the noun, `AgentSchedule` or `AgentSession`; whether `Remove-AgentSchedule`
ends a running tmux session; `Set-AgentSchedule` when the schedule already has a claude session, replacing it or
refusing it as Start-Claude does with 73; `Set-AgentSchedule` on a running claude session; and whether a new
schedule's first claude session is made by `Start-AgentSchedule` or by `New-AgentSchedule`. That issue also lists
where the owner's design departs from Start-Claude; with the background model, the store keeps the background
session's id, and the startup hook is gone. Later, the owner, 2026-10-13: "One day the agent-assignment commands
become a star extension; not now."

## Appendix: the agent-assignment design, as the owner wrote it (2026-10-13)

From NobleFactor/noblefactor-ops#302, word for word, its lines wrapped at 120 columns.

```text
Agent Assignment Commands

Purpose

The agent-assignment command set manages persistent AI agent assignments. An assignment connects an agent session to a
GitHub schedule and provides an interactive terminal environment for carrying out the work.

The initial commands are:

* Start-AgentAssignment: create or resume an assignment and open its terminal environment.
* Get-AgentAssignment: retrieve assignments, including their identity, runtime state, and progress against their
schedules.

Command names use approved PowerShell verbs across both shell and PowerShell implementations. Parameters follow each
platform’s conventions while retaining equivalent meaning.

The commands support configurable agents. Claude Code is the initial implementation; other terminal agents, such as
Codex CLI, can be supported through agent-specific adapters.

Conceptual Model

An assignment associates three objects with different lifetimes:

Object    Role    Lifetime
Schedule    GitHub issue linking to the issues to complete    Stable across restarts
Agent session    Agent context used to execute the schedule    Persistent across terminal sessions
tmux session    Agent pane and companion terminal pane    Ephemeral and recreatable

The assignment is the durable association between these objects. A tmux session disappearing does not delete the
assignment or change its schedule.

The agent’s objective is to work through the issues linked from the schedule. Existing GitHub-assignment and
GitHub-progress skills define how the agent interprets its assignment and records progress. The commands manage the
environment and retrieve its state.

Assignment Identity

A schedule number is only unique within a GitHub repository. An assignment therefore needs a repository-qualified
schedule reference.

For the initial design, allow one assignment per repository and schedule within the current user’s assignment store on
a host. The clone directory is an execution location, not the assignment’s identity.

Each assignment receives an immutable identifier. Its record includes:

* Assignment identifier.
* GitHub repository and schedule issue number.
* Canonical clone directory.
* Configured agent and persistent agent session identifier.
* tmux session name.
* Creation and last-started timestamps.
* State format version.

The tmux name is an access reference. The assignment remains valid when that session no longer exists.

Persistent Storage

Store assignment records beneath:

${XDG_DATA_HOME:-$HOME/.local/share}/agent-assignment

The Windows implementation should resolve an equivalent per-user application data location through a shared storage
convention.

Use one directory per assignment, containing a structured metadata file and any launcher-owned bootstrap or recovery
information.

The assignment store holds references to agent sessions. Agent-native conversation data remains in the agent’s own
storage.

Write metadata atomically and serialize concurrent starts for the same assignment. A failed launch must leave enough
information to distinguish an existing resumable agent session from an assignment that has not yet created one.

Start-AgentAssignment

Responsibility

Create or resume an assignment, ensure its tmux environment is available, and attach the user to it.

Shell example:

mosh host -- Start-AgentAssignment --directory clone --schedule 916

PowerShell invocation:

Start-AgentAssignment -Directory clone -Schedule 916

Proposed Interface

Shell parameter    PowerShell parameter    Meaning
--directory <path>    -Directory <path>    Clone used to resolve the repository and execute the work; defaults to the
current directory
--schedule <number>    -Schedule <number>    GitHub schedule issue number; required
--agent <name>    -Agent <name>    Agent for a new assignment; defaults to the configured agent
--no-attach    -NoAttach    Ensure the assignment is running, then return without attaching

For an existing assignment, the stored agent is authoritative. An explicit conflicting agent parameter produces an
error; it does not silently replace the agent session.

Start Behavior

1. Resolve the clone directory and GitHub repository.
2. Find the assignment associated with that repository and schedule.
3. Acquire an assignment-specific lock.
4. Inspect stored metadata and actual tmux state.
5. Create or restore the required environment.
6. Persist any updated references.
7. Release the lock and attach, unless attachment was disabled.

For a new assignment, validate the schedule, create the assignment record, initialize an agent session, and create the
two-pane tmux environment.

For an existing assignment with a running agent, attach to the existing environment without launching another agent.

For an existing assignment whose tmux session is missing, recreate the environment and resume the stored agent session.

If the tmux session exists but the agent process has exited, preserve the terminal pane and resume the agent in the
agent pane.

Repeated starts must converge on the same assignment and must not create duplicate agent processes.

Terminal Environment

The tmux session contains:

* An agent pane running the assignment’s configured agent.
* A terminal pane opened in the assignment’s clone directory.

Use a deterministic, collision-resistant tmux name derived from the assignment identifier. Mark the session with
assignment metadata so the launcher can verify ownership before reusing it.

Detaching leaves the assignment running. If invoked from within tmux, switch to the assignment session rather than
attempting a nested attachment.

On Windows, tmux is psmux, a native Windows tmux run as `tmux`, its alias: the owner's ruling of 2026-10-10, proven on
danoble-wd11-3 in David-Noble-at-work/personal#273. Windows Terminal's panes, which Start-Claude.ps1 opened before,
were dropped. The owner, 2026-10-17: "we dropped wt in favor of psmux because wt is a GUI app that won't run on a
terminal or in any remote session".

Agent Bootstrap and Resumption

For a new agent session, provide:

* The repository and clone location.
* The schedule issue reference.
* The objective of working through its linked issues.
* Instructions to use GitHub-assignment and GitHub-progress according to their defined contracts.

For an existing session, resume its saved context. Do not replay initialization as though it were a new assignment.

The adapter must reliably obtain the agent session identifier and persist it as soon as it is available. If the stored
session cannot be resumed, report the failure explicitly. Do not silently create a replacement session.

Failure Handling

Validate prerequisites before launching a new assignment: the directory, repository, schedule access, tmux, and
configured agent.

A temporary GitHub outage should not prevent attachment to an already-running assignment whose identity is known
locally.

If the recorded clone has moved or disappeared, report the mismatch and require an explicit directory selection. Do not
infer a replacement clone.

Get-AgentAssignment

Responsibility

Retrieve a read-only view of assignments, combining locally observed runtime state with progress recorded in GitHub.

The command must not start an agent, recreate tmux sessions, attach to a session, or modify GitHub issues.

Proposed Interface

Shell parameter    PowerShell parameter    Meaning
--directory <path>    -Directory <path>    Filter by the repository associated with this clone
--schedule <number>    -Schedule <number>    Retrieve one schedule’s assignment; resolve its repository from the
directory parameter or current directory
--all    -All    Retrieve all assignments in the current user’s store on this host
--local    -Local    Skip GitHub queries and retrieve local state only
--json    Not required    Serialize shell output as JSON; PowerShell uses ConvertTo-Json

With no selector, retrieve assignments for the current repository. Outside a repository, require the all-assignments
parameter or an explicit directory.

The all-assignments parameter is mutually exclusive with repository and schedule filters.

Shell examples:

Get-AgentAssignment --schedule 916
Get-AgentAssignment --directory clone --schedule 916
Get-AgentAssignment --all
Get-AgentAssignment --all --local --json

PowerShell examples:

Get-AgentAssignment -Schedule 916
Get-AgentAssignment -Directory clone -Schedule 916
Get-AgentAssignment -All | Format-Table
Get-AgentAssignment -All -Local | ConvertTo-Json -Depth 10

Output Contract

The PowerShell implementation returns one structured object per assignment. It does not write formatted tables or
descriptive prose to the success output stream.

Default PowerShell formatting presents a concise summary. Users can inspect details, select properties, filter
assignments, and serialize results using standard pipeline commands.

The shell implementation displays a readable summary by default and emits structured data when --json is specified.
JSON output must represent the same assignment information exposed by the PowerShell objects.

Display formatting must not change which data is retrieved. Retrieving one assignment or many uses the same object
structure.

Assignment Information

Each returned assignment includes:

Category    Fields
Identity    Assignment identifier, repository, schedule number and URL
Execution    Clone directory, configured agent, agent session identifier
Terminal    tmux session name, presence, attached client count
Agent runtime    Process present, exited, or unknown
Progress    Linked issue counts, issue-level details, and progress information recorded under the existing skill
conventions
Timestamps    Assignment creation, last start, observation time
Problems    Missing directory, unavailable agent session, inaccessible GitHub data, inconsistent metadata

Human-readable shell output can show issue-level detail for a single assignment and a compact summary for multiple
assignments. Structured output retains the retrieved details in either case.

Runtime State and Work Progress

Expose runtime state separately from schedule progress.

A live tmux session does not prove that the agent is running. A running agent process does not prove that it is
actively making progress. An absent tmux session does not imply that the assignment is complete.

Use locally observable runtime states:

* Running: the assignment’s agent process is present in its expected pane.
* Stopped: metadata exists, but the agent is not running.
* Degraded: required local resources are missing or inconsistent.
* Unknown: runtime inspection could not establish the state.

Return issue counts separately, such as total linked issues, open issues, and closed issues. Treat closure as issue
status, not proof of successful completion. Include completion reasons and richer progress states when the existing
GitHub conventions provide them.

Do not infer “working,” “waiting for input,” or “blocked” by scraping terminal text. Such states require a defined
agent status signal.

Data Sources and Partial Failure

The local assignment record is authoritative for identity and session associations. Live tmux inspection is
authoritative for terminal presence. GitHub is authoritative for schedule and issue progress.

Use the schedule membership rules established by GitHub-assignment; do not introduce a second interpretation of which
links constitute assigned work.

If GitHub is unavailable, return local assignment information with progress marked unavailable. Distinguish progress
that was not requested through the local-only option from progress that could not be retrieved.

If cached progress is introduced later, label it with its retrieval time.

When retrieving multiple assignments, a failure inspecting one assignment must not prevent returning the others.
Structured output must include per-assignment problems and distinguish unavailable data from empty results.

PowerShell diagnostics use the appropriate error or warning streams without contaminating returned assignment objects.
Shell diagnostics go to standard error, preserving machine-readable standard output.

Agent Adapter Contract

Agent-specific behavior belongs behind a small adapter interface:

* Validate agent availability.
* Start a new agent session with assignment context.
* Obtain its persistent session identifier.
* Resume an existing session.
* Determine whether the agent process is present.

The shared command layer owns assignment identity, storage, locking, tmux layout, repository resolution, and state
retrieval.

Adapters implement agent-specific operations within the common assignment lifecycle.

Scope

The first version supports persistent assignment creation, resumption, attachment, and read-only retrieval.

It does not automatically restart agents, migrate assignments between hosts, replace lost agent sessions, or decide
whether work is complete independently of the GitHub workflow.

Acceptance Criteria

* Starting the same repository and schedule twice reuses one assignment and agent session.
* Concurrent starts do not create duplicate sessions or agent processes.
* Recreating tmux preserves the agent session association.
* Reattaching does not resend new-assignment instructions.
* Different repositories can use the same schedule number without collision.
* Retrieval distinguishes terminal presence, agent process state, and issue progress.
* Retrieval works with no active tmux session.
* GitHub failures preserve useful local results.
* A failed resume is visible and never silently becomes a new agent session.
* PowerShell returns structured assignment objects suitable for pipelines.
* Shell JSON output exposes equivalent assignment information.
* Human-readable formatting and diagnostics do not corrupt structured output.
```
