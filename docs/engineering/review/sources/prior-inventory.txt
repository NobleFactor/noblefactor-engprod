# Existing process requirements inventory

This is a read-only inventory of locally available requirements and implementations, not a compliance verdict on current work. No GitHub state, installed binary provenance, branch protection settings, approval history, or CI results were queried. No git commands, builds, or tests were run. Repository files were not changed. The report is outside the repositories pending a decision about its issue and permanent home.

Scope: the engineering-process worktree, the devlore-cli worktree's instructions and Makefile, and the deployed personal Claude instructions. Historical plans and proposed architecture are supporting evidence, not automatically current requirements. Language rules are grouped by independently useful compliance checks rather than one row per sentence. Personal memory files and the live errors-of-judgment issue #317 were not inspected; this is therefore a baseline inventory of the accessible process, not a claim to have enumerated every historical ruling.

## Reading the inventory

- **Implemented** means a concrete check or helper was found in source. It does not mean it was executed, deployed, required everywhere, or impossible to bypass.
- **Template** means the documented script contains the operation; each generated script must still include it correctly.
- **Manual** means review or operator behavior is currently needed; no dedicated automatic check was established in the inspected sources.
- **Proposed** means the architecture/status documents describe unfinished tooling.
- Source keys below link to full local paths. Section names identify the relevant requirements.

## Consolidation findings requiring decisions

1. **Plan template contradicts the process it is meant to support.** PT tells readers to copy a subject-named file and then create the issue. DP requires issue first, issue-derived path, committed plan and review before implementation. PT also lacks the required stable issue heading in its example structure.
2. **Release guide conflicts with newer workflow and protection documents.** RP teaches in-place checkout/branching, `bugfix/*` (absent from the allowed prefix regex), direct pushes, and protected-branch merge commits. DP requires issue-bound worktrees; BP documents PR-only/squash/linear protected history. Do not silently reconcile these examples as equally usable procedures.
3. **Plan completion has a boundary ambiguity.** DP says last PR commit sets complete when boxes are ticked, but also permits an active plan with outstanding boxes; AR12 explicitly keeps plans active for post-merge work. A machine needs distinct implementation-complete and deployment/verification evidence, or an explicit approved exception rule.
4. **Blocking work and committed schedules need reconciliation.** IS forbids additions to a committed schedule except joint deliverable replanning; DP says an external blocking PR defect is filed and put on the schedule as a lane. Define the required amendment/authorization path.
5. **Blocked-worktree handling needs a preservation rule.** AR8 orders immediate removal/deletion on blocking; DP describes resolving a blocker and returning, or keeping entangled work in the current worktree. These prescriptions need explicit conditions and preservation evidence.
6. **Session identity has evolved.** DP describes one session per issue and feature-based titles; assignment/session documents and current skills bind persistent sessions to schedules. Establish a single current lifecycle model and adapter-specific implementation instructions.
7. **Issue schema is transitioning.** IS still describes kind labels/body parent markers; Model and code also read native types/parent links and check disagreement. Specify authoritative fields, compatibility/migration boundaries and eventual removal of duplicate representations.
8. **Schedule rendering is more permissive than the rule.** Source accepts epic tokens and larger units, ignores header validity, and does not establish contiguous numbering or unique live membership. Displaying a table is not schedule validation.
9. **No generic cross-asset compliance gate was found.** Frontmatter validity does not verify issue → plan → design → branch → PR → deployment relationships, approved ordering, or freshness.
10. **Script safeguards are copied obligations.** Critical merge, span, lane-update and cleanup behavior lives in generated scripts. The manifest provides report/audit/labels/model commands, but no dedicated issue-create, schedule-transition, PR-span or whole-process compliance command.
11. **Read-only clones are specified, not demonstrated as enforced.** Existing symlinks establish location only. The sandbox companion explicitly marks read-only clone support as not started.
12. **Enforcement scope must be explicit.** engprod CI runs Make gates, but source existence does not show every repository adopted each gate, that local scripts match the template, or that current GitHub rulesets match the documented settings. Admin merge bypass is explicitly documented.
13. **Architecture impact needs inspectable evidence.** The documents allow no design document for no architectural effect, but no mandatory impact determination was found. Today absence of a design row cannot distinguish “reviewed; none” from “forgotten.”
14. **Documentation authority and provenance need normalization.** Personal directives still link to noblefactor-ops while the current workspace is noblefactor-engprod; redirects may preserve links, but authoritative location/version and precedence should be stated. Historical rulings can remain rationale without being necessary to reconstruct the active rule.

## What this inventory supports next

The first consolidation deliverable can be a requirement register with stable IDs, applicability, authoritative definition, evidence schema, check implementation and lifecycle trigger. Keep the five concerns connected: schedules; workflow; tools; coding standards; issue/plan/design assets. Migrate the rules above into that register only after resolving conflicts; attach historical incidents as rationale and regression cases. Prefer extending existing star commands and shared Make gates over introducing another independent interpretation of the process.
